Why TrimScale CSS?

In print, leading is the space between lines, and nothing else. CSS sees it differently. Every line box splits its extra line-height above and below the text, and adds whatever room the font designer left above the capitals and below the baseline. The result is a heading that never quite sits flush with the image next to it, and a 24px gap that is really 24px plus whatever the font felt like that day.

The project started with a photography website, built by hand rather than in a drag-and-drop editor, from a background in design and 3D visualization where a two-pixel misalignment counts as a bug. Tutorials showed how to space text, rarely why it behaved the way it did. The usual answer was a magic number per font, which holds up right until someone changes the font.

Chasing the why turned into a degree project, Precision Typography Toolkit: a polyfill for text-box-trim and an interactive tool for extracting the font metrics it needs. A few months later that work became TrimScale CSS, and then a config-driven npm package that works with the fonts a project actually uses, not just the ones it was tested on.

It reads your font files at build time and handles three things magic numbers can't: leading-trim that removes the space above caps and below the baseline, side-bearing adjustment that aligns text with its edges horizontally too, and a line height that recalculates itself for any font size. All from one config file.

Around that sits the rest of a base system. A fluid type scale that stretches smoothly between viewports instead of jumping at breakpoints, spacing that can follow the type scale or stand on its own, OKLCH color tokens with automatic fallbacks for older browsers, and metric-matched fallback fonts so nothing shifts when the web font loads. Tokens, utility classes and cascade layers are all generated from one config file, as SCSS or as plain CSS.

Leading Trim

Leading trim removes the space CSS adds above the capitals and below the baseline, so a text box starts at the cap height and ends at the baseline. The spacing you write is then the spacing you see.

Both columns below have the same visible space between blocks. The blue stripes show the gap each one needed to get there.

Without trim

This box includes the line height (half-leading) above and below the text.

The gap above this paragraph is 1em, and the line height adds to what you see.

With trim

This box starts at the top of the first line's capitals and ends on the last line's baseline.

The gap above this paragraph is 1.5em, and so is the space you see.

Without trim, a 1em gap looks more like 1.5em, because each line box brings its own share of hidden space. How much depends on the font and the line height, so the number in your CSS never quite matches the page. With trim, the gap is 1.5em and it looks like 1.5em.

Every font role in your config gets a trim class, like .trim-text-heading or .trim-text-body, and the font-setup mixin does the same inside your own components. Browsers with native text-box-trim use it directly. Older ones get a fallback built from the font metrics TrimScale reads at build time.

Getting Started

One install, one config file, one generate command. Everything runs at build time, so nothing from the package ends up in your JavaScript bundle.

Requirements

  • Node.js 22.18
  • Sass 1.95

  1. Install

    Add the package as a dev dependency. 

    npm install -D trimscale-css
    pnpm add -D trimscale-css
    yarn add -D trimscale-css

  2. Initialize

    Copies trimscale.config.ts into your project root and adds a trimscale:generate script to your package.json. 

    npx trimscale-css init
    pnpm dlx trimscale-css init
    yarn dlx trimscale-css init

  3. Configure

    Fonts, type scale, breakpoints, spacing and colors all live in trimscale.config.ts. This is the font setup behind the page you're reading: 

    appFonts: {
  localFontsPath: 'public/fonts',
  families: {
    'roboto': {
      source: 'local',
      fallback: { matched: 'sans-serif' },
    },
    'roboto-serif': {
      source: 'local',
      fallback: { matched: 'serif' },
    },
    'roboto-mono': {
      source: 'local',
      fallback: { matched: 'monospace' },
    },
  },
  fontRoles: {
    primary: 'roboto-serif',
    heading: 'roboto-serif',
    body: 'roboto',
    code: 'roboto-mono',
  },
},

    Every role gets its own trim class and font token, so heading above becomes .trim-text-heading. Fonts are optional: without appFonts you still get the type scale, spacing and colors, just no leading trim. See this page's full config.

  4. Generate

    Reads your config and font files and writes the result into ./trimscale-generated, inside your own project. Run it again whenever the config changes. 

    npm run trimscale:generate
    pnpm trimscale:generate
    yarn trimscale:generate

  5. Import

    Use it as SCSS, or as a vanilla CSS file with no Sass setup at all.

    Point Sass at the package, then load the generated files once at your entry point. 

    // vite.config.ts
export default {
  css: {
    preprocessorOptions: {
      scss: {
        loadPaths: ['node_modules/trimscale-css/styles'],
      },
    },
  },
};
    // main.scss
@use './trimscale-generated';

    Turn on the CSS output, generate again, and link the bundle. You get the same tokens and utility classes, without the SCSS mixins. 

    // trimscale.config.ts
output: { css: true },
    <link
  rel="stylesheet"
  href="/trimscale-generated/trimscale.bundle.min.css"
/>

  6. Trim your first heading

    Add a trim class in your markup, or use the font-setup mixin in your own components. 

    <h2 class="trim-text-heading">Flush with the grid</h2>
    @use 'abstracts/mixins' as mx;

.card__title {
  @include mx.font-setup(
    $font: 'heading',
    $font-size: var(--heading-3)
  );
}

Next.js, the pkg: importer and the rest of the setup details are in the full getting started guide.

Design Tokens

Every token is a CSS custom property, generated from trimscale.config.ts. The values below are this page's own, measured live. Resize the window and watch the fluid ones change.

Type scale

Semantic sizes on top of a fluid modular scale. Each one is a clamp() between a mobile and a desktop ratio, or a fixed fraction of another size.

Font families

Each family is used by one or more roles, and every role gets a --font-family-* token of its own.

Font weights

Line heights work the same way, from --line-height-100 to --line-height-200 in increments of 5. Most text never needs them: it gets --line-height-dynamic, which recalculates itself for any font size.

Spacing

Two units. Small steps build on a fixed micro unit and stay put, large steps build on a fluid macro unit and grow with the viewport. A numeric scale, --space-1 and up, sits alongside the named sizes.

Colors

OKLCH tokens with light-dark() switching and a hex fallback for older browsers. Semantic aliases reference a base token and adjust it, instead of adding another hand-picked pair.

Fluid Functions

Fluid values scale linearly with the viewport between the two widths in fluidScale, and hold still outside them. Every fluid token on this page comes from the functions below. They are SCSS functions, so calling them yourself needs the SCSS setup; the plain CSS bundle ships their results as tokens instead.

Fluid values

$fluid-scale

The viewport range every fluid function interpolates across, generated from fluidScale in the config. This page's values: 

$fluid-scale: (
  "min-width": 360,
  "max-width": 1440,
  "min-font-size": 16,
  "max-font-size": 20,
  "min-type-scale": 1.2,
  "max-type-scale": 1.333,
  "precision": 4,
);

fn.fluid-value takes a size for the narrowest viewport and one for the widest, and returns the clamp() between them. Reach for it when a value belongs on neither the type scale nor the spacing scale, like an icon size or a component's own padding. With $type: 'max' there is no ceiling, and the value keeps growing past the widest viewport instead of stopping there.

The line is the formula. The dot is an element on this page that uses it, measured live, so it follows when you resize the window. Tick Simulate to drag a width instead.

Fluid font sizes

fn.fluid-font-size takes a step on the modular scale instead of two sizes. Both ends come from $fluid-scale: the base size times the mobile ratio at the narrowest viewport, times the desktop ratio at the widest. The desktop ratio is the larger one, so the scale spreads as the screen grows. Body text barely moves, display sizes more than double. Every whole step of the scale is one of these lines.

The chart's height is logarithmic, so an even ratio between steps shows as an even gap.

Dynamic line height

$dynamic-line-height

The two pinned points and the cap the curve is drawn from, generated from dynamicLineHeight in the config. This page uses the defaults: 

$dynamic-line-height: (
  "fs-base": 16,
  "ratio-base": 1.5,
  "fs-ceil": 64,
  "ratio-ceil": 1.05,
  "ratio-cap": 1.6,
);

Keep it unregistered. --line-height-dynamic only works as an unregistered custom property. Registered with @property, it resolves once at the root, and every element inherits the same number.

A line height that suits body text is far too loose on a large heading. fn.dynamic-line-height tightens it as the font size grows, between the two points in the note, and caps it for small text. It resolves per element when the page renders, against that element's own font size, so one declaration covers every size on the page, including sizes that aren't on the type scale.
