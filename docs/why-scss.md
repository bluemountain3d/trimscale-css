# Why SCSS

Nesting, custom properties, `@layer`, `@container`, `color-mix()`,
`light-dark()`, relative color syntax: the two things people originally
reached for a preprocessor to get, variables and nesting, have both shipped
natively. Reaching for SCSS today to avoid writing `&:hover` would be habit,
not engineering.

trimscale-css uses SCSS anyway, for four things CSS still can't do. None of
them are stylistic.

**Nothing ships to the browser.** SCSS is the build step. The output is plain
CSS with custom properties: no runtime, no JavaScript, no dependency on Sass
existing anywhere past your build.

---

## 1. Generating rules from data

The utility classes are `@each` loops over Sass maps. Spacing alone is a
numeric scale × `{margin, padding}` × `{none, t, r, b, l, x, y}`, plus the
t-shirt scale on top. Typography classes loop over your configured font
roles, sizes, and weights.

CSS has no way to iterate over a data structure and emit rules from it.
Custom properties are values; they aren't structures you can walk at compile
time. `@function` (Chromium-only as of this writing) computes values, it
doesn't generate selectors.

Without loops, [`utility-classes.md`](utility-classes.md) would be a
hand-maintained file several hundred entries long, regenerated by hand every
time you touch a config field.

---

## 2. Build-time font data

Leading trim needs your font's ascender, descender, and cap height. Metric-
matched fallbacks need a width average derived from the `hmtx` table. Those
values live inside the font binary. There is no CSS API that exposes them,
and there won't be one, the browser uses them internally but doesn't
surface them to the cascade.

So the numbers have to be extracted before any CSS exists. `generate` parses
your font files and writes the results into the bridge file, which configures
the SCSS at your own compile time. This is the part of the system that is
categorically not expressible in CSS, now or later.

---

## 3. Partials with a namespace

`@use 'abstracts/mixins' as mx` gives three things at once: the file splits,
the names are namespaced, and the module loads once no matter how many files
`@use` it.

CSS's `@import` gives none of them. It's textual inclusion with no namespace
and no collision protection, discovered sequentially, each level of the chain
is a fresh round trip before the next one is even known, and all of it blocks
rendering. With a bundler the loading problem goes away, but the namespace
problem doesn't.

It's worth being precise about why this gap has stayed open. Nesting was
simply missing, so CSS added it. A module system needs something to attach
names to, and the cascade has no scoping concept to attach them to: rules are
global by nature and files arrive in arbitrary order. `@layer` solved ordering
and `@scope` solved subtree boundaries, but neither is a namespace. A CSS
module system would have to invent one first.

---

## 4. Mixins that wrap at-rules

```scss
@include mx.and-up('tablet') {
  width: 300px;
}
```

expands to `@media (width >= 45rem)`, with the value resolved from your
configured breakpoints map.

There's no CSS equivalent, and the reason is specific: `var()` doesn't work
inside media query conditions. `@media (width >= var(--bp-tablet))` is invalid.
So breakpoint values can't be tokens, they have to be substituted before the
CSS is parsed, which means a build step.

The same applies to [`mx.font-setup`](abstracts.md#mxfont-setup), which
`@extend`s a font-role placeholder so one shared trim rule covers every
caller, and to
[`mx.generate-color-tokens`](abstracts.md#mxgenerate-color-tokenstokens-default-scheme),
which emits a three-tier `@supports` fallback chain per token from a single
source map.

---

## What SCSS is *not* used for here

- **Variables.** Every token in the system is a CSS custom property, so it's
  overridable at runtime, inspectable in devtools, and scoped by the cascade.
  Sass variables appear only where a value must be resolved at compile time
  (breakpoints in media queries, font metrics, loop sources).
- **Nesting.** Used for readability, but native nesting would do the job
  everywhere except selector concatenation, which this codebase avoids anyway.
- **Color math.** Colors go through OKLCH and `light-dark()` in the output,
  not through `sass:color`.

---

## What this costs you

Being straight about the trade-off: SCSS is a real dependency for consumers.
You need Dart Sass 1.95.0+, `loadPaths` configured for your bundler, and the
`pkg:` importer registered separately if you want it, and `pkg:` doesn't work
in Next.js at all, which is why Next.js has
[its own page](using-with-nextjs.md).

If you only want the tokens and utility classes and none of the authoring API,
that's a lot of setup for what amounts to a stylesheet. See
[getting-started.md](getting-started.md#standalone-css-output) for the
standalone CSS output, which skips the Sass configuration entirely at your
bundler, `generate` still compiles it for you at generate time.

The SCSS path is what you choose when you want `mx.font-setup`, the breakpoint
mixins, and the font-role placeholders in your own component styles. It isn't
an entry fee.
